# ADR 0002 서버와 화면을 TypeScript 한 언어로 만든다

## 맥락

레포에는 `README.md` 한 개뿐이라 언어·프레임워크가 정해져 있지 않다(`README.md:1`). 1차 오픈 목표는 6주이고(`plan/requirements.md#NFR-05`), 승인된 아키텍처는 입력 검증 규칙과 오류 코드의 정본을 하나로 두고 서버와 화면이 같이 쓰라고 정했다(`S3-D14`). 개발팀의 기술 스택은 입력에 없다(기술 스펙 가정 A-12).

## 결정

서버, 웹 화면, 둘이 같이 쓰는 코드를 모두 TypeScript(strict)로 쓰고 서버는 Node.js 24 LTS 에서 Fastify 로 돌린다. `api/openapi.yaml` 을 정본으로 서버는 시작할 때 Ajv 로 컴파일해 검증하고, 화면은 같은 명세에서 빌드 때 타입과 검증 함수를 생성해 쓴다(결정 id S4-D1, S4-D16).

## 고려한 대안

- Java/Spring Boot 서버 + 별도 화면 프로젝트: 사내 서버 환경에 익숙한 선택일 수 있으나, 검증 규칙과 상수를 두 언어로 따로 옮기거나 생성기를 추가로 들여야 하고 6주 일정에 도구가 늘어난다.
- Go 서버 + 별도 화면 프로젝트: 배포는 단순하지만 화면과 같은 검증 함수를 공유할 수 없어 같은 이유로 정본이 둘이 되기 쉽다.
- 서버 렌더링(Python/Django 등)으로 화면까지 한 서버: 언어는 하나지만 영역별 재시도·대화상자 초점 관리가 필요한 화면 설계(`plan/ui-spec.md#4`)를 서버 템플릿으로 맞추기 어렵다.

## 결과와 대가

- 서버와 화면이 같은 검증 규칙·상수·오류 문구를 명세에서 받아 어긋남이 컴파일과 CI 에서 잡힌다.
- 개발팀이 TypeScript 와 Node.js 를 다룰 수 있다는 가정에 기댄다. 틀리면 가장 먼저 일정이 흔들리고, 언어를 바꾸면 서버·화면·시험 도구가 모두 다시 정해진다. 이미 쓴 코드를 다른 언어로 옮기는 비용이 커서 되돌리기 어렵다.
- Node.js 의 실행 환경(런타임 버전)을 운영 서버에 맞춰야 하고, 배포는 빌드가 끝난 묶음을 올리는 방식으로 한다(기술 스펙 2.3절).
